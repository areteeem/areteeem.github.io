Act as a skeptical reviewer whose job is to find weaknesses in the proposed idea before it is built or launched.

Do not try to defend the idea. Stress-test it.

Analyze the idea from the perspective of:

* the target user
* a first-time user
* a power user
* someone who does not trust the product
* someone who already has an alternative workflow
* a technical reviewer
* a business reviewer
* a privacy/security reviewer
* an investor or judge
* someone actively trying to break the system

First, restate the idea in 3 to 5 sentences so it is clear what you are evaluating.

Then challenge the core assumptions.

Identify:

* assumptions about user behavior
* assumptions about what users actually need
* assumptions about willingness to change existing habits
* assumptions about technical feasibility
* assumptions about data availability
* assumptions about accuracy
* assumptions about integrations or third-party services
* assumptions about pricing or monetization
* assumptions about scale
* assumptions about legal, privacy, security, or compliance requirements

For every major assumption, answer:

* What must be true for this assumption to hold?
* How likely is it to be true?
* What evidence would prove or disprove it?
* What happens to the product if it is false?

Find scenarios where the product fails or becomes significantly less useful.

Include scenarios involving:

* users behaving differently than expected
* missing, incomplete, incorrect, or outdated data
* AI producing incorrect outputs
* false positives
* false negatives
* edge cases
* unreliable APIs
* unavailable integrations
* slow responses
* poor internet connection
* unsupported devices
* accessibility issues
* users misunderstanding the interface
* users ignoring recommendations
* users intentionally misusing the product
* malicious users
* privacy-sensitive situations
* unusually large inputs
* unusual user workflows
* multiple users editing or acting at the same time
* rapid growth
* very low usage
* changes in third-party pricing or API limits
* competitors copying the feature
* users deciding that an existing simpler solution is good enough

For each failure scenario, provide:

* scenario
* why it could realistically happen
* probability: low / medium / high
* severity: low / medium / high / critical
* what exactly breaks
* whether the current idea handles it
* possible mitigation
* whether the mitigation adds major complexity

Ask at least 20 difficult questions that the founder or developer should be able to answer before building the full product.

Prioritize questions such as:

* Why would someone use this instead of their current workflow?
* What happens if the main feature is wrong 10% of the time?
* What happens if it is wrong 1% of the time in a high-risk situation?
* What part of the product requires the most user trust?
* Which feature sounds impressive but may provide little practical value?
* Which feature could be removed without substantially reducing user value?
* What is the hardest dependency outside our control?
* What happens if a third-party API disappears?
* What is the easiest way for a competitor to reproduce this?
* What would make a user stop using the product after one week?
* What would make a user refuse to try it at all?
* Is the problem frequent enough for users to care?
* Is the problem painful enough for users to pay or change habits?
* Does the solution create additional work for the user?
* Does it require data the user may not have?
* Where could automation make the workflow worse?
* Which decisions still require a human?
* What is the worst possible outcome caused by an incorrect result?
* What happens when two system rules conflict?
* What happens when the system is uncertain?

Look specifically for "demo works, real life fails" problems.

Identify features that:

* look good during a presentation
* work with controlled demo data
* become unreliable with real users
* depend on manually prepared data
* require integrations that would be hard to obtain
* require partnerships before the product becomes useful
* would require much more engineering than they initially appear to

Separate the product into:

* must work perfectly
* can occasionally fail
* optional
* unnecessary complexity

Identify the single weakest part of the idea.

Then identify the three most likely reasons the entire product could fail.

Also provide:

* strongest argument against building it
* strongest argument for continuing
* easiest cheaper alternative to the product
* strongest existing alternative users could choose instead
* what would make this idea 10x simpler
* what would make this idea 10x more useful
* what should be tested before writing substantial code

Design 5 adversarial user tests.

Each test should include:

* user type
* situation
* task
* unexpected behavior or edge case
* expected system response
* failure condition

Finish with a verdict using this format:

Overall viability: X/10

User need: X/10
Technical feasibility: X/10
Real-world reliability: X/10
Differentiation: X/10
Ease of adoption: X/10
Business viability: X/10

Biggest risk:
[one concise explanation]

Most dangerous untested assumption:
[one concise explanation]

First thing to validate:
[one concrete test]

Features to remove or postpone:
[list]

Questions that must be answered before proceeding:
[the 5 most important unanswered questions]

Recommendation:

* proceed
* proceed only after validation
* significantly simplify
* pivot
* stop

Be critical and specific. Do not invent problems merely to fill space. Distinguish between realistic risks and unlikely theoretical edge cases. If a concern depends on missing information, ask a direct question instead of assuming the answer.
